## Voice

- Write like one software engineer casually sharing what he worked on, not like a product account explaining Career OS.
- Start from the actual dev moment: `spent too long on...`, `added... today`, `this broke because...`, `decided to...`, `still not sure about...`.
- Friendly, humble, curious, occasionally fun, and technically precise. It is fine to sound unfinished because the product is unfinished.
- Do not mention `Career OS` in every post. People already know what the thread is about.
- Never structure a post as hook, product explanation, polished takeaway. Never end with a slogan, a neat moral, or a sentence such as `small choice, much cleaner reality`.
- Avoid product-marketing verbs and framing such as `empowers`, `turns X into Y`, `only then does it...`, `built X into Career OS`, `designed to`, or `this changes every...`.
- Prefer the wording a developer could type in 30 seconds after closing the editor. Contractions, lowercase, fragments, and mild uncertainty are welcome when natural.
- Before publishing, read it aloud. If it sounds like launch copy, a LinkedIn post, or something a brand account would write, rewrite it as a plain build note.
- One idea per post.
- Short sentences. First person when possible.
- No generic launch language, fake excitement, emojis, engagement bait, or invented metrics.
- Use a real product screenshot, code diff, terminal result, or no image. Never use decorative AI art.
- Do not claim that the managed cloud service exists yet.

Good:

> spent way too long deciding whether a saved job should already count as an application.
>
> decided no. it only becomes one when you actually start working on it.

> added saved search profiles today. hard filters can remove a job, preferences only change the order.
>
> still not sure how i want to handle missing salary or remote info tbh.

Bad:

> I built saved search profiles into Career OS. Small data-model choice. Much cleaner reality.

The bad version packages the work as a product benefit and lands on a polished conclusion. Do not publish that voice.

## Visual system

A raw full-screen capture is evidence, not a finished marketing asset. When a post needs a visual, turn the real source into a polished 16:9 Career OS card before publishing.

- Export at 3200 x 1800 PNG.
- Use a small factual build-log line when context is needed. Do not turn every visual into an ad headline.
- Crop or zoom the product to the exact feature being discussed; the UI should occupy most of the frame and remain readable in the X feed.
- Use the Career OS lockup, dark ink background, white product surface, and one restrained violet accent.
- Add one small context label such as `DAY 4`, `BUILD LOG`, `PRIVACY`, or `YOUR CALL` only when it helps the story.
- Keep generous negative space, clean alignment, subtle depth, and one obvious focal point. Product UI should usually occupy 75-85% of the frame.
- Reuse actual UI, code, diffs, tests, or terminal evidence. Redact personal data and secrets.
- Never use oversized landing-page typography, benefit chips, stacked slogans, a fake device frame, stock 3D object, neon glow pile, decorative robot, or generated illustration.

Use one of three formats:

1. **Feature hero:** short hook plus one enlarged product interaction.
2. **Proof card:** claim on the left, real diff/test/evidence on the right.
3. **Product question:** short question plus one UI decision being debated; no generic quote card.

For the strongest visual milestones, prefer a **three-panel panorama** inspired by the current X product-design format:

- compose one continuous `3600 x 2000` master from real product UI;
- split it vertically into three ordered `1200 x 2000` PNGs: left, center, right;
- keep the background, product surface, and visual rhythm continuous across all three files;
- when the screen benefits from more depth, place it on a restrained atmospheric brand backdrop: warm ink, very dark violet, subtle grain, and soft directional light. The backdrop supports the UI; it must not become the subject;
- keep the product surface clearly separated with a fine edge and restrained shadow. Do not use stock scenery or a decorative generated scene just to fill space;
- keep important UI and text away from the two seams;
- upload all three in left-to-right order so the feed reveals the product as a swipeable panorama;
- use it only when the underlying screen is genuinely strong enough to carry the post; there is no frequency target.

Before proposing publication, check that the hook and the core UI detail are legible at 50% size. If the source cannot produce a strong composition, publish text only.

## Milestone replacement rule

- visible user impact;
- a non-obvious product or engineering decision;
- executable proof, a real screenshot, or a measurable result;

For a milestone post, produce exactly:

1. one short post under 240 characters when possible;
2. one alternate hook;
3. one real visual recommendation;
4. the commit or file that supports every factual claim.
